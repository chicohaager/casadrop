Configuration Guide

CasaDrop — Network configuration & webhooks

Two things decide whether CasaDrop is actually useful: whether the link you hand someone opens on their device, and whether your other systems find out when a file moves. This guide covers both — the Network panel and its five access paths, and webhook notifications end to end, with every claim measured against a running build.

1 Before you start

Both areas in this guide live behind Settings, and Settings is admin only. A user with the User or Viewer role does not see the Settings tab at all, and the underlying endpoints (/api/tunnel, /api/webhook, /api/webhook/test) reject them.

You will need shell access to the host for some of this. A few settings exist only as environment variables and cannot be changed from the interface — which ones is called out at each point rather than left for you to discover.

If you are still on 2.4.4, four things behave differently from what is described here. All four were silent — a wrong result with no error message — and all four are fixed in 2.4.5. Upgrade, or read the marked "On 2.4.4" notes as you go:

  • The Webhook form in Settings could not arm a webhook at all (§12).
  • Saving that form erased a stored signing secret (§12).
  • The expire event never fired, in any configuration (§11).
  • The Local Network address typed in Settings was displayed back but was not the one baked into share links (§4).

2 How a share link is built

Read this section first. Almost every "the link doesn't work" report is explained here.

When CasaDrop creates a share, it has to decide what hostname to put in front of /s/<id>. It does not simply use your Primary network selection. It asks two questions, in this order:

1. Was this request made through a public-looking hostname?
If the address in the admin's browser bar is anything other than localhost, a .local name, a loopback address or a private-range IP, that hostname wins and the Primary network selection is ignored entirely.
2. Otherwise: what is the Primary network?
The radio button you selected in Settings decides, using that network's URL.
3. Otherwise: the address the request came in on.
Fallback when the selected network has no URL configured.

Measured against a running instance with Cloudflare selected as the primary network:

Admin browsing viaLink that gets generatedWhy
127.0.0.1:8080https://demo.trycloudflare.com/s/…loopback → primary network decides
192.168.10.20:8080https://demo.trycloudflare.com/s/…private IP → primary network decides
nas.local:8080https://demo.trycloudflare.com/s/….local → primary network decides
files.example.comhttp://files.example.com/s/…public name → overrides the primary network

Rule 1 is deliberate and usually what you want: if you reached CasaDrop through your reverse proxy, the links you create should also go through your reverse proxy. It only surprises you when you did not realise the name you are using counts as public.

A .lan name counts as public; a .local name does not. Only localhost, *.local and literal private/loopback/link-local IP addresses are treated as internal. Any other DNS name — nas.lan, casadrop.home.arpa, an internal Active Directory name — is treated as a public hostname and takes over link generation.

Note the http:// in the last row. Even when the proxy in front of CasaDrop terminates TLS, the generated link stays http:// until you set TRUSTED_PROXY. See §8.

3 The Network panel

Settings → Network Configuration. Five cards, one per access path. Each card has three controls:

ControlWhat it does
Checkbox (left of the name) Enables the network. Unchecking it greys the card out, stops the value being offered anywhere, and skips auto-detection for it.
Primary (radio) Exactly one network is primary. It supplies the hostname for every new share link, receive link and QR code — subject to the override in §2. The radio is disabled while the card is unchecked.
Text field The URL or IP. Pre-filled with the auto-detected value where one exists; anything you type overrides detection permanently.

Below the field, a card shows Detected: … when CasaDrop found a value on its own, plus a Use detected button when your typed value differs from it. Under the cards sits Max file size (1–100 GB; values outside that are clamped, and 0 falls back to the default of 10 GB).

Nothing takes effect until you press Save. One save writes all five cards plus the size limit at once.

Where it is stored. <DATA_DIR>/tunnel_config.json. The file is cached in memory for 30 seconds, so a value edited on disk by hand can take up to half a minute to appear.

Validation on save

The save is rejected as a whole (HTTP 400) if any field fails:

  • Cloudflare and Tailscale must be https://. Plain http:// is refused.
  • Custom Domain accepts http:// or https://, so a LAN reverse proxy without TLS still works.
  • EasyTier must be a bare IP address — no scheme, no port.
  • Every URL needs a host part; a bare path is refused.

4 Local network

Sharing inside your own LAN. The default primary network.

The field expects a bare IPv4 address — no scheme, no port. CasaDrop appends http:// and the external port itself, producing http://192.168.10.20:8080/s/<id>.

Auto-detection

Two independent detectors run, and it matters which one wins:

  • The container entrypoint reads ip -4 route get 1.1.1.1 and exports the result as LOCAL_IP. It falls back to hostname -i.
  • The application separately walks the network interfaces, skipping loopback, tailscale*, tun*, easytier* and anything in 172.*. This is the value shown as Detected in the panel.

The address you type here wins over auto-detection and over the LOCAL_IP environment variable, which remains the fallback when the field is empty. That ordering matters in bridged Docker, where the entrypoint's detection returns the container's own 172.x address — a value nobody on your LAN can reach. Typing the host's real address in Settings is enough to correct it.

On 2.4.4 this field was display-only. Link generation read the LOCAL_IP environment variable and never the typed value, so the panel reported one address while every link carried another:

Settings panel shows primaryUrl = http://192.168.10.20:8080 Actual link handed out http://172.18.0.5:8080/s/44e506f2

On 2.4.4, set LOCAL_IP in the environment as shown below; from 2.4.5 either place works, with Settings taking precedence.

Setting it in the environment instead

Still useful when you would rather pin it outside the interface:

# docker-compose.yaml, casadrop service
environment:
  - LOCAL_IP=192.168.10.20        # your host's real LAN address
  - EXTERNAL_PORT=8080            # the published port, if not 8080

Then docker compose up -d. A docker compose restart is not enough — it does not re-read the environment block.

EXTERNAL_PORT, not PORT. PORT is the port inside the container; EXTERNAL_PORT is the one that goes into links. If you publish CasaDrop on host port 8085, set EXTERNAL_PORT=8085 or every local link will point at the wrong port.

5 Cloudflare Tunnel

Public HTTPS from behind NAT, no port forwarding, no fixed IP.

There are two modes and they behave very differently.

Quick tunnel

No Cloudflare account. cloudflared mints a random https://<words>.trycloudflare.com address. Free, instant, and gone when the container restarts. For handing someone a file this afternoon.

docker compose --profile tunnel up -d

Named (token) tunnel

Needs a Cloudflare account and a tunnel token. The hostname is fixed in the Cloudflare dashboard and survives restarts. For a link that has to keep working.

CLOUDFLARE_TUNNEL_TOKEN=xxx \
  docker compose --profile tunnel up -d

How the URL reaches CasaDrop

The tunnel runs in its own container. It shares the /data volume with the app and writes the address it obtained to <DATA_DIR>/tunnel_url.txt; CasaDrop reads that file. For a token tunnel the wrapper writes the literal word token instead, which CasaDrop recognises and ignores — you supply the real hostname yourself, via the Cloudflare Tunnel field or TUNNEL_URL.

Precedence when CasaDrop resolves the Cloudflare address:

  1. What you typed in the Settings field.
  2. tunnel_url.txt, written by the tunnel container.
  3. The TUNNEL_URL environment variable.

Selecting Cloudflare mints a fresh URL

This is intentional and worth understanding before you trip over it. When you switch the primary network to Cloudflare — only on that transition — CasaDrop asks the tunnel container to throw away the current quick-tunnel address and mint a new one. The design goal is a throwaway link per errand.

Every rotation kills the previously shared link. If you handed out a trycloudflare.com address an hour ago and then re-select Cloudflare, that address stops working. For links that must survive, use a named token tunnel, Tailscale, or your own domain.

Measured behaviour of the trigger:

ActionRotation
Primary changes from anything → CloudflareYes — response carries cloudflareRotating: true
Save again while Cloudflare is already primaryNo — an unrelated settings save never kills a live link
Token tunnel active (tunnel_url.txt = token)No — a fixed hostname has nothing to rotate

While rotating, the interface shows "Generating a fresh Cloudflare share URL…" and polls for up to about 60 seconds. If no tunnel container is running you get "No new Cloudflare URL appeared — is the tunnel container running?", which is exactly what it sounds like.

6 Tailscale Funnel

A stable public HTTPS name, no Cloudflare account, no rotation.

The field takes the full HTTPS URL of your node, e.g. https://casadrop.tailnet-example.ts.net. It must be https://.

Auto-detection

Three sources, first hit wins:

  1. <DATA_DIR>/tailscale_url.txt, if present.
  2. tailscale status --json, if the tailscale binary is on PATH inside the container. CasaDrop reads Self.DNSName, strips the trailing dot and prefixes https://. It only accepts the value when the node reports itself online.
  3. The TAILSCALE_URL environment variable.

Two ways to run it

Sidecar container. The bundled profile shares the app's network namespace, so localhost:8080 inside the sidecar is CasaDrop:

TAILSCALE_AUTHKEY=tskey-xxx TAILSCALE_HOSTNAME=casadrop \
  docker compose --profile tailscale up -d

# then enable the funnel once
docker exec casadrop-tailscale tailscale funnel --bg 8080

An existing Tailscale container. If your host already runs one, point its funnel at CasaDrop's published port and set the URL by hand:

docker exec <your-tailscale-container> \
  tailscale funnel --bg --https=443 http://localhost:8085

# then in CasaDrop:
TAILSCALE_URL=https://<host>.<tailnet>.ts.net

Funnel must be enabled for the node in the Tailscale admin console first. The tailscale funnel command fails without it, and CasaDrop's detection will simply report nothing rather than explaining why.

Funnel is public; the tailnet address is not. Funnel exposes CasaDrop to the open internet. If you only want your own devices to reach it, skip Funnel and use the node's plain tailnet name or its 100.x address in the Custom Domain / URL field instead.

7 EasyTier

Mesh VPN. Replaced ZeroTier as the mesh option on ZimaOS.

The field takes a bare IPv4 address of your node on the mesh — no scheme, no port. CasaDrop builds http://<ip>:<EXTERNAL_PORT>/s/<id>, the same shape as the local network. A value that is not a parseable IP address is rejected on save.

Auto-detection

Four attempts, in order:

  1. easytier-cli peer list — first line mentioning local or self, first parseable IP on it.
  2. easytier-cli connector list — first non-loopback IPv4 found.
  3. Interface scan for names starting tun or easytier.
  4. The EASYTIER_IP environment variable.

None of the first three work in a default bridged container. The easytier-cli binary is not in the image and the mesh interface belongs to the host, not the container. Either give the container the host network (network_mode: host), bind-mount easytier-cli read-only, or simply set EASYTIER_IP and skip detection entirely. The last option is the least trouble.

8 Custom domain & reverse proxies

Your own hostname: nginx, Caddy, Traefik, Pangolin/Newt, WireGuard.

This card is a free-text field and is never auto-detected. Put in the full public base URL, with scheme, no trailing path: https://files.example.com. Both http:// and https:// are accepted, so an internal proxy without TLS works too.

Set TRUSTED_PROXY — this is not optional

CasaDrop ignores X-Forwarded-For, X-Forwarded-Host and X-Forwarded-Proto unless the peer that sent them is listed in TRUSTED_PROXY. That default is deliberate: without it, any client could forge those headers and control the hostname baked into your share links, or evade the per-IP rate limits and account lockout.

The cost of leaving it unset behind a proxy, measured:

ConfigurationGenerated link
TRUSTED_PROXY unset, proxy sends X-Forwarded-Proto: https http://files.example.com/s/… wrong scheme
TRUSTED_PROXY=127.0.0.1/32, same request https://files.example.com/s/… correct

Set it to the address your proxy connects from, as seen by CasaDrop — comma-separated CIDRs or plain IPs:

environment:
  - TRUSTED_PROXY=172.18.0.0/16      # the Docker bridge the proxy sits on
  # or
  - TRUSTED_PROXY=192.168.10.5,10.10.0.0/24

Do not set TRUSTED_PROXY to 0.0.0.0/0. That trusts every client to declare its own IP address and hostname, which restores exactly the spoofing the setting exists to prevent — including bypassing brute-force lockout by rotating a header.

Pangolin / Newt

Pangolin needs no dedicated setting. Links follow the incoming Host/X-Forwarded-Host header (§2), so as long as you reach CasaDrop through the Pangolin hostname, the links match. Set TRUSTED_PROXY so the scheme comes out as https.

Minimum proxy configuration

# nginx
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
client_max_body_size 0;          # CasaDrop enforces its own limit
proxy_request_buffering off;     # stream large uploads instead of spooling

Ready-made compose files for Caddy, Traefik and Authentik ship in docs/.

10 Network troubleshooting

The link I sent points at an address nobody can reach

Read §2 first — check what hostname you used when you created the share. Then check what CasaDrop thinks it should be producing:

curl -s -b cookies.txt http://<host>:<port>/api/network | python3 -m json.tool

Compare primaryUrl with a link you actually generated. If they differ and the primary network is local, you have hit the LOCAL_IP problem in §4 — the panel is showing you the value you typed, not the value in use.

Detected shows the container's 172.x address

Expected in bridged Docker. Set LOCAL_IP explicitly and recreate the container.

Links are http:// but my site is https://

TRUSTED_PROXY is unset. §8.

Tailscale shows Not detected

The tailscale binary is not reachable from inside the app container, or the node reports itself offline. Both are normal for the sidecar setup — set TAILSCALE_URL by hand rather than fighting detection.

A saved URL is refused

Cloudflare and Tailscale require https://; EasyTier requires a bare IP with no scheme and no port. The error names the field.

My Cloudflare link died on its own

Either the container restarted (quick-tunnel addresses do not survive), or someone re-selected Cloudflare as the primary network, which rotates on purpose. §5.

A change in Settings did not take effect

The config is cached for 30 seconds. If it is still wrong after a minute, the value is being overridden by an environment variable — check the container's environment.

11 Webhooks — what they are

A webhook is an HTTP POST that CasaDrop sends to a URL of your choosing when something happens. The body is JSON. Use it to drive a chat notification, an automation flow, a log, or anything that speaks HTTP.

CasaDrop has two independent webhook systems, and they do not share configuration, headers or payload shape:

Global webhookReceive-link webhook
Configured inSettings → Webhook (one per instance)Per receive link, at creation time
Fires onDownloads, download-limit reachedSomeone uploads a file to that link
SignedYes — X-Webhook-SignatureNo signature at all
Event headerX-Webhook-Eventnone
User-AgentZima-Share/1.1Zima-Share/1.0
Stored inwebhook_config.jsonThe receive link's database row

Events

EventFires whenStatus
downloadAnyone downloads or streams a shared fileworks
limit_reachedThe download reaching a share's max_downloadsworks
file_receivedA file is uploaded to a receive linkworks
expireThe hourly cleanup removes an expired shareworks 2.4.5+

The expire event is emitted by the cleanup sweep, which runs hourly. A share therefore reports its expiry up to an hour after the timestamp passed — the event marks the moment the file was actually deleted, not the moment the link stopped working. The payload carries the share's final download count.

On 2.4.4 the expire event never fired. The flag could be set to true and the sending function existed, but nothing called it — the cleanup had no connection to the webhook service. An automation waiting for expire on 2.4.4 waits forever.

When a download exhausts a share's limit, both download and limit_reached are sent, as two separate deliveries. They are dispatched concurrently, so the order they arrive in is not guaranteed — do not write a receiver that assumes one precedes the other.

Delivery behaviour

  • Fire and forget. Delivery happens in the background. The download the user requested succeeds regardless of whether your endpoint answers.
  • No retries. A failed delivery is logged and dropped. If your receiver is down, the event is gone.
  • 10-second timeout per delivery.
  • Redirects are refused. A 302 is not followed — point the webhook at its final destination.
  • 32 concurrent deliveries maximum. Beyond that, events are dropped with a log line rather than queued.
  • On shutdown, in-flight deliveries get up to 5 seconds to finish.

12 Setting up the global webhook

Route A — Settings → Webhook

The card carries everything the feature needs:

  1. Webhook enabled — the master switch. Nothing is sent while it is off, whatever else is filled in.
  2. Webhook URL — the target. See §15 for which hosts are permitted.
  3. Notify on — one checkbox per event: file downloaded, download limit reached, share expired.
  4. Webhook Secret — optional HMAC key. The field is always blank when the page loads, because the API never sends a stored secret back; the placeholder tells you which case you are in.
  5. Save, then Test Webhook.

How the secret field behaves. Leave it blank and the stored secret is kept — blank means "unchanged", never "erase". Type a value to replace it. To remove one, tick Remove the stored secret, which only appears when a secret is actually stored. The placeholder reads "unchanged — leave blank to keep" or "no secret set" accordingly, so you can always tell whether one exists without being shown its value.

On 2.4.4, do not use this card. It had only URL and Secret fields and no enable or event checkboxes, so saving it stored enabled: false / on_download: false and silently disarmed the webhook — Test Webhook then answered HTTP 400 — Webhook not configured:

POST /api/webhook {"url":"…","secret":"…"} → 200 {"status":"ok"} GET /api/webhook → enabled:false on_download:false POST /api/webhook/test → 400 "Webhook not configured"

Worse, the blank Secret field was written back on every save, silently erasing a stored signing secret (measured: "s3cr3t" → null) and breaking the receiver's signature checks with no message anywhere. On 2.4.4 use Route B or C below and leave the card alone.

Route B — the API

The same endpoint the form uses. Any field you omit keeps its stored value, so a one-line call can flip a single setting without disturbing the rest.

# 1. log in and keep the session cookie
curl -s -c cookies.txt -X POST https://files.example.com/login \
     -H 'Content-Type: application/json' \
     -d '{"password":"<your admin password>"}'

# 2. write the full configuration
curl -s -b cookies.txt -X POST https://files.example.com/api/webhook \
     -H 'Content-Type: application/json' \
     -d '{
           "enabled": true,
           "url": "https://hooks.example.com/casadrop",
           "on_download": true,
           "on_limit_reached": true,
           "secret": "a-long-random-string"
         }'

# 3. prove it
curl -s -b cookies.txt -X POST https://files.example.com/api/webhook/test

Field by field:

FieldMeaning
enabledMaster switch. Without true nothing is ever sent. Enabling with an empty URL is refused (400).
urlTarget. http or https; see §15 for which hosts are permitted.
on_downloadSend the download event.
on_limit_reachedSend the limit_reached event.
on_expireSend the expire event when the cleanup deletes an expired share.
secretOptional HMAC key. Present ⇒ every delivery is signed. Omit the key to keep the stored secret; send "" to remove it.

A 200 from the test endpoint does not mean delivery succeeded. It means the notification was handed to the background sender. A blocked or unreachable target still returns {"status":"test notification sent"}. Confirm at the receiving end, or read the container log — §16.

Route C — environment variables

Simplest for a fixed deployment. Applied at startup, and they override whatever is in webhook_config.json:

environment:
  - WEBHOOK_URL=https://hooks.example.com/casadrop
  - WEBHOOK_SECRET=a-long-random-string

This sets enabled: true and on_download: true. It does not enable on_limit_reached or on_expire — for those use Route A or B. The variables are re-applied on every start, so a config written through the interface or the API is overridden again after a restart.

WEBHOOK_URL is always checked against the SSRF guard, and STRICT_WEBHOOK_URLS=false does not exempt it. Measured: with both opt-outs set, WEBHOOK_URL=http://127.0.0.1:8791/env is still discarded, with one line in the log and nothing in the interface:

Webhook: ignoring WEBHOOK_URL from env: webhook URL must not target a private or loopback address

A literal private or loopback IP in WEBHOOK_URL can never work. Use a hostname instead — see §15.

Reading the configuration back

GET /api/webhook reports every setting and whether a secret is stored, but never the secret itself:

{
  "enabled": true,
  "url": "https://hooks.example.com/casadrop",
  "on_download": true,
  "on_expire": true,
  "on_limit_reached": true,
  "secret_set": true
}

The payload

Recorded from a real download:

POST /hook HTTP/1.1
Content-Type: application/json
User-Agent: Zima-Share/1.1
X-Webhook-Event: download
X-Webhook-Signature: sha256=244d2e38a34b5c7d…

{
  "event": "download",
  "share_id": "43dce6dc",
  "file_name": "demo.txt",
  "downloads": 1,
  "timestamp": "2026-09-07T14:51:21.418576866+02:00",
  "client_ip": "203.0.113.44",
  "user_agent": "Mozilla/5.0 …"
}

client_ip and user_agent are present on download only; limit_reached omits both. downloads is the counter after the download that triggered the event.

client_ip is only meaningful if TRUSTED_PROXY is set. Behind a reverse proxy without it, every event reports your proxy's address rather than the visitor's. Same setting as §8, second reason to get it right.

13 Verifying the signature

With a secret configured, every global-webhook delivery carries:

X-Webhook-Signature: sha256=<hex>

The value is HMAC-SHA256 over the raw request body, hex-encoded, with the literal prefix sha256=. Independently reproduced from a captured delivery:

$ echo -n "$BODY" | openssl dgst -sha256 -hmac "s3cr3t" -r
c6e5d425512602f1f942dbdef9ff8afac445f729605e906db2b943de4f03bf20

# header CasaDrop sent
X-Webhook-Signature: sha256=c6e5d425512602f1f942dbdef9ff8afac445f729605e906db2b943de4f03bf20

Hash the raw bytes, not a re-serialised object. Parsing the JSON and dumping it again changes the whitespace and key order, and the signature will never match. Capture the body before your framework touches it.

Python

import hmac, hashlib

def valid(raw_body: bytes, header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(
        secret.encode(), raw_body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, header or "")

Node.js

const crypto = require('crypto');

function valid(rawBody, header, secret) {
  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret).update(rawBody).digest('hex');
  const a = Buffer.from(expected), b = Buffer.from(header || '');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

Always compare in constant time (compare_digest, timingSafeEqual) rather than with ==.

Without a secret there is no signature header at all — anyone who learns your webhook URL can post convincing fake events to it. Set a secret unless the endpoint is otherwise authenticated.

14 Receive-link webhooks

A receive link lets people upload files to you. Each link can carry its own webhook, fired when a file arrives. This is separate from the global webhook; both can be active at once.

Set it when creating the link:

curl -s -b cookies.txt -X POST https://files.example.com/api/receive-links \
     -H 'Content-Type: application/json' \
     -d '{
           "name": "Client uploads",
           "max_uploads": 10,
           "auto_share": true,
           "webhook_url": "https://hooks.example.com/casadrop-receive"
         }'

Recorded from a real anonymous upload:

POST /receive HTTP/1.1
Content-Type: application/json
User-Agent: Zima-Share/1.0

{
  "event": "file_received",
  "receive_link": "50d94287",
  "receive_name": "Client uploads",
  "file_id": "adbc5a59",
  "file_name": "demo.txt",
  "file_size": 15,
  "uploader_ip": "203.0.113.44",
  "timestamp": "2026-09-07T14:51:43.673454729+02:00",
  "share_id": "1e0f933d"
}

share_id appears only when the link has auto_share enabled, which turns each arriving file into a share automatically.

These deliveries are not signed. There is no X-Webhook-Signature and no X-Webhook-Event header — the event name is in the body only. A receiver cannot verify that a file_received POST really came from CasaDrop. Protect the endpoint another way: an unguessable path, a bearer token in the URL, or an IP allow-list.

Same delivery rules as the global webhook: fire-and-forget, 10-second timeout, no retries, redirects refused, and the same SSRF guard applies to webhook_url at link-creation time — a private-IP target is rejected with HTTP 400 when you create the link.

15 The SSRF guard

Webhook URLs are attacker-influenceable — anyone who can create a receive link can ask CasaDrop to make an HTTP request. Left open, that turns your file server into a probe for everything on your internal network, including cloud metadata endpoints. CasaDrop therefore refuses private targets by default.

There are two layers, and they catch different things:

LayerWhenCatchesOpt-out
URL validationOn save A literal private, loopback or link-local IP in the URL STRICT_WEBHOOK_URLS=false
Dial-time checkOn every delivery A hostname that resolves to a blocked address — including DNS rebinding after the URL was approved WEBHOOK_STRICT_SSRF=false

Measured against a default instance:

Webhook URLResult
http://192.168.10.20:9000/hook400 — must not target a private or loopback address
http://127.0.0.1:8791/hook400 — same
ftp://example.com/x400 — URL must use HTTP or HTTPS
https://hooks.example.com/casadrop200 — accepted
http://localhost:8791/hooksaved, never delivered — passes validation as a name, blocked at dial time

That last row is the confusing one and it is worth showing what it looks like. The save succeeds, the test reports success, and nothing arrives. The only evidence is in the container log:

Webhook: failed to send request: Post "http://localhost:8791/hook": ssrf: refusing to connect to blocked address 127.0.0.1

Sending to a receiver on your own LAN

A legitimate homelab need — n8n, Home Assistant, Gotify, ntfy on the same network. The measured working recipe is a hostname plus the dial-time opt-out:

environment:
  # a NAME, not a literal private IP — a literal IP is rejected
  # even with the opt-outs below
  - WEBHOOK_URL=http://ntfy.lan:8080/casadrop
  - WEBHOOK_SECRET=a-long-random-string
  # allow the delivery to land on a private address
  - WEBHOOK_STRICT_SSRF=false

Configuring a private target through the API instead of the environment additionally needs STRICT_WEBHOOK_URLS=false, since that is the layer which rejects the literal IP on save.

Neither variable is present in the shipped compose files. WEBHOOK_STRICT_SSRF is passed through with a default of true; STRICT_WEBHOOK_URLS is not listed at all. To use either opt-out you must add the line to the environment: block yourself.

Turn these off only if CasaDrop is not reachable by strangers. They are on by default because CasaDrop is designed to be internet-exposed and receive links let anonymous visitors influence webhook targets. On a publicly-reachable instance, leave both at their defaults and put your notification receiver behind a name that resolves publicly.

16 Webhook troubleshooting

Every webhook outcome is logged. Start here, always:

docker logs casadrop 2>&1 | grep -i webhook
Log lineMeaning
successfully sent <event> notification for share <id>Delivered, receiver answered below 400.
received error status <n>Delivered, but your endpoint returned 4xx/5xx. Not retried.
failed to send request: …Never reached the endpoint. The rest of the line says why — DNS, timeout, or ssrf: refusing to connect.
ignoring WEBHOOK_URL from env: …The environment variable was discarded at startup (§12).
delivery budget exhausted, dropping …More than 32 deliveries in flight. Your receiver is too slow.

Test Webhook says "Webhook not configured" (400)

The stored configuration has enabled: false or an empty URL. Tick Webhook enabled and save. On 2.4.4 this was the normal outcome of saving the Settings card at all — see §12.

Test says sent, nothing arrives

Three measured causes, in order of likelihood:

  1. The SSRF guard blocked the dial. The log line begins ssrf: refusing to connect. §15.
  2. The URL redirects. Redirects are refused by design — use the final URL.
  3. The receiver is unreachable or slower than 10 seconds.

Signature checks started failing and nothing changed

Check whether the secret is still stored: GET /api/webhook reports secret_set. On 2.4.4, opening Settings → Webhook and pressing Save erased it (§12); from 2.4.5 a blank field means "keep", and only the explicit Remove the stored secret checkbox clears one.

I get download events but never limit_reached

on_limit_reached is false. If you configured via WEBHOOK_URL, only on_download is switched on — use the API to enable the rest.

I never get expire events

On 2.4.4 the event did not exist — upgrade (§11). From 2.4.5, check that on_expire is set, and remember the sweep is hourly: a share that expired four minutes ago has not been swept yet.

Verifying without touching production

A three-line receiver is enough to see exactly what CasaDrop sends:

python3 - <<'EOF'
import http.server
class H(http.server.BaseHTTPRequestHandler):
    def do_POST(self):
        n = int(self.headers.get('Content-Length', 0))
        print(dict(self.headers)); print(self.rfile.read(n).decode())
        self.send_response(200); self.end_headers()
http.server.HTTPServer(('0.0.0.0', 8791), H).serve_forever()
EOF

Point the webhook at it by hostname and remember WEBHOOK_STRICT_SSRF=false if it is on a private address.

The five settings that cause the most trouble

  1. LOCAL_IP — set it in the environment. The Settings field looks authoritative and is not (§4).
  2. EXTERNAL_PORT — set it whenever the published port is not 8080.
  3. TRUSTED_PROXY — set it behind any reverse proxy, or links come out as http:// and every client_ip is your proxy (§8).
  4. Webhook enabled — the webhook does nothing without it; on 2.4.4 the Settings form could not set it at all (§12).
  5. WEBHOOK_STRICT_SSRF — the reason a correctly configured LAN webhook silently delivers nothing (§15).

If you only remember three things

  • The hostname in your browser bar can silently override the Primary network you selected. When a link looks wrong, check how you reached the interface.
  • A webhook needs its master switch on and at least one event ticked; a blank Secret field means "keep the stored one", not "erase it".
  • A green "test notification sent" only means the message was queued. Confirm at the receiving end or in docker logs.
